# Развёртывание сайта

## Как устроено в проекте

Сайт **статический**, исходники лежат в каталоге [`site/`](../site/) внутри GitHub-репозитория. Публикация выполняется **через хостинг-агрегатор** (статический хостинг), который подключён к репозиторию: платформа сама подтягивает код после push и выкладывает файлы на CDN без настройки Ubuntu, Nginx и собственного VPS.

Примеры таких сервисов: **GitHub Pages**, **Netlify**, **Vercel**, **Cloudflare Pages**, **Render** (Static Site) и аналоги. Конкретный сервис и URL проекта фиксируются в отчёте по факту настройки.

## Общая схема

```text
Локальные изменения
      |
      | git commit && git push
      v
GitHub (ветка с сайтом, например main)
      |
      | webhook / polling
      v
Хостинг-агрегатор (сборка при необходимости + выкладка)
      |
      v
Публичный HTTPS URL (выдаётся платформой)
```

Отдельный Linux-сервер с ручным `git pull` и Nginx в этом потоке **не участвует** — всё делает связка «GitHub + выбранная платформа».

## Настройка на стороне агрегатора

Общая логика (детали меняются по интерфейсу конкретного сервиса):

1. **Подключить репозиторий** — авторизация через GitHub, выбор org/user и имени repo.
2. **Указать ветку** — обычно `main` (или та, где лежит проект).
3. **Задать корень публикации** — каталог **`site/`**, чтобы в корне сайта оказались `index.html`, `about.html`, `team.html`, `blog.html`, `resources.html` и подпапки `css/`, `js/`, `images/`. Это важно: если указать корень репозитория, главная по адресу `/` не откроется из `site/index.html` без дополнительных редиректов.
4. **Сборка (build)** — для текущего проекта отдельная команда сборки не нужна: достаточно режима «static», «no build» или эквивалента.
5. **Сохранить** — после первого успешного деплоя платформа выдаёт постоянный URL (и при желании настраивается свой домен).

### Почему на Netlify «не деплоится» или пустой сайт

Частая ошибка для этой разметки репозитория: Netlify берёт по умолчанию **Publish directory** = `.` (корень монорепозитория). В корне нет **`index.html`** — только папки `docs/`, `site/`, `src/`. Итог: деплой проходит технически, но открывается **пустая страница**, **«Page not found»** или стандартный экран без вашей вёрстки.

**Что сделать в Netlify (Site settings → Build & deploy → Build settings):**

| Параметр | Значение |
|---------|----------|
| **Base directory** | _(пусто)_ — корень репозитория |
| **Build command** | _(пусто)_ или любая no-op, сборки нет |
| **Publish directory** | **`site`** |

Либо положите в корень GitHub-репозитория файл [`netlify.toml`](../netlify.toml) из этого проекта: в нём указано `publish = "site"` — после `push` Netlify подхватит каталог без ручного ввода в UI.

Дополнительно проверьте: репозиторий реально залит на GitHub (Netlify тянет с GitHub, а не с локальной папки); выбрана верная ветка; билд не «падает» из‑за лишней команды (`npm run build`, если не настроена среда) — её нужно удалить или оставить пустой.

## Обновление сайта

Любое изменение в `site/` после `git push` в подключённую ветку инициирует **новый деплой** автоматически (иногда с задержкой в десятки секунд или пару минут). Ручное копирование файлов на сервер не требуется.

## Проверка после публикации

Рекомендуется проверить:

- главная страница открывается и отдаёт успешный ответ (ожидаемо **`200 OK`**);
- переходы по всем пунктам меню (`about`, `team`, `blog`, `resources`) без **404**;
- внешние картинки и ссылка на ВКонтакте открываются с браузера пользователя (зависит от политики сторонних хостингов изображений, не от агрегатора).

## Telegram-бот

Процесс бота описан в [`telegram_bot.md`](telegram_bot.md). Бот реализован как отдельная вариативная часть и разворачивается отдельно от статики: статический хостинг обслуживает только **`site/`**, а процесс бота запускается в отдельной среде (локально, на приложенческом хостинге или VPS).

## Результат

Публичный сайт должен соответствовать содержимому каталога **`site/`** в репозитории после последнего успешного деплоя, чтобы относительные ссылки между `*.html` работали без изменения путей.
